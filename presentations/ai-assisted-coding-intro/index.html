Encode what you do in prompts, then iterate automatically

Correct as you go — manual prompting in chat. You are the loop: prompt, look, prompt again.

Plan first, then execute — manually prompt a plan into existence, then execute and let it rip, correcting when needed. This is where a plan.md or a tool’s plan mode comes in: the plan is worked out with the LLM first, or you use an LLM to generate a self-contained prompt that encodes the goal, the checkpoints, and how to verify each checkpoint.

Reusable workflow — as you mature into plan-making, the items that turn up in every plan go through the same process: you extract the skills that produce acceptable results out of your own loop. A pre-set skill per step, collected in an orchestrator prompt that knows how to use them.

Bonus: abstract one step further out and make a skill that composes the workflow dynamically, according to the problem.

Requirements

Goal: clear requirements, functional and non functional.

StepWhat it covers
GatherLet the agent act as a PM and drill you one question at a time, prodding for edge cases.
Refine ticketsTurn the raw requirements into structured ones using User Stories, EARS and Gherkin.
Scope trimmingRun INVEST over the user stories to isolate one vertical slice, then rebuild the requirements around it.
Narrative optionalWrite the spec so a less technical audience can review it.
Narrative: there is no industry standard for this one the way there is for the rows above it. What has worked for me is Joel Spolsky's four-part series on writing functional specs, logically condensed into a skill.

Goal: working code that satisfies the requirements.

StepWhat it covers

A workflow you can read

PhaseCommandLeaves behind
01DrillA spec — the questions asked, the answers given
02PrototypeA clickable screen, before any code exists
03RefineThe spec again, every assumption checked against the source
04ImplementA branch, failing tests first, then a pull request
05QAA report, posted to that pull request

QA is not allowed to read the code it is checking.

Five checked-in commands, one per phase. The point is the third column: every phase ends in something a human can read and disagree with, rather than one opaque run. The QA line is the one to land — a suite written by whatever wrote the code is not independent evidence, so that phase judges the feature by running it. The workflow is versioned and reviewable, which means someone else can run it.

Demo

One command, five phases

One command runs the whole loop. Collect is the only phase that asks anything; the rest run without intervention. Idle gaps are capped at two seconds, so the pauses are visible but not real time. If time is short, skip to the Linear ticket — the five comments carry the argument on their own. Two moments worth telling, both from this run, neither staged. First: /craft:audit caught a real contradiction that nobody had noticed. The requirements said the error banner shows the server's message. The audit cited the line — Http.expectJson discards the response body on a non-2xx, so the server's message never reaches the view — and corrected the requirement rather than growing unrequested HTTP plumbing to satisfy it. It also noted the prototype had independently done the same thing. That is the hub working: the phase validated against the requirements and against the code, and reported the disagreement instead of picking a side quietly. Second: /craft:forge declined to overclaim. It reported that three of its service tests were green on their first run, because they pin behaviour the server already had, so the genuine red-then-green happened only at the browser tier. Nothing forced it to say that. An agent volunteering that part of its own red-green was theatre is the most credible line in the whole artifact — and it is the reason to trust the rest of the report.

A run that halts at a named check
is the system working.
It looks like the system failing.

That is why each phase leaves something behind.

This is the failure mode worth naming out loud. A black box that ends in "I could not do it" is indistinguishable from incompetence. A run that stops at a stated check, with the reason on screen, is legibly a system doing its job — but only if the reason is on screen. If the harness stops during the demo, that is the demo.

Cool Tricks

Beyond writing the code

TrickWhat it covers
During incidentsConnect the agent to live logs alongside the repo to triage likely root causes.
Post mortemsHave the agent generate monitoring dashboards for what the incident exposed.
Infrastructure as codePoint the implementation workflow at Terraform or CDK instead of service code.
Load testingHave the agent load test the service, then improve and revalidate against the results.
Isolated worktreesDevelop features in parallel, with an isolated stack per worktree.
Incidents: handle with care, agents love red herrings. Worktrees also require real familiarity with the workflows before they pay off.
